# http-client-msw — design contract

`@archon-research/http-client-msw` derives msw request handlers from a generated
OpenAPI `paths` type. This document is the authoritative statement of what the
layer guarantees, what it deliberately refuses to do, and why.

## Premise: the generated `paths` type is the endpoint definition

There is exactly one description of the API in a consuming app: the
`openapi-typescript` output. The same `paths` type drives three layers —
`createApiClient` (http-client-core), `createQueryApi` (http-client-react), and
`createMockApi` here — so a mock and the request it stands in for are described
by one source.

That is the whole reason the package exists. A hand-written fixture drifts: the
API renames a field, the fixture keeps the old one, every test that reads it
keeps passing, and the app breaks in production against a contract the test suite
claimed to cover. Here the drift is a compile error — the handler's path, its path
and query params, its request body, its status codes, and the body it returns for
each status are all read off the operation.

## Verdict on `openapi-msw`

We considered hand-rolling the typed handler factory over plain `msw` and
**depended on `openapi-msw@2.0.0`** instead. This is the opposite call from
http-client-react's on `openapi-react-query`, and the contrast is the argument.

**Dependency weight.** Zero runtime dependencies. `msw` is its only peer — the
same peer this package declares — so it adds no second version constraint to
satisfy. MIT, ~96 KB unpacked, of which the substance is `.d.ts`; the runtime is
a `path.replaceAll('{', ':')` conversion, a resolver wrapper, and a response
helper.

**Type fidelity to the output we generate.** It reads exactly the shape
`uikit-openapi-generate` emits: `parameters.path` and `parameters.query`
stringified (arrays unboxed to their element type), `requestBody.content` keyed
by media type, `responses[status].content` keyed by media type, `content?: never`
mapped to a no-content response, and OpenAPI status wildcards (`2XX`, `default`)
expanded to the concrete codes they allow. Critically it also handles
`openapi-typescript`'s absent-operation encoding — `put?: never` — so a handler
factory offers only the paths that declare its method.

`src/mock-api.types.test.ts` is what holds that claim: it asserts the positive
inference and `@ts-expect-error`s the six ways a fixture drifts — unknown path,
method absent on a path, wrong response shape, wrong response *cardinality* (an
object where the operation returns a list), undeclared status code, and unknown
query param. Those negatives are the guarantee, and they are checked by
`npm run type:check` rather than trusted.

**API fit.** `mock.get('/things/{id}', resolver)` with brace templates converted
to msw's colon form is the surface we would have designed. The resolver gets msw's
own info object plus a typed `query` reader and a per-status `response` helper
(`response(200).json(body)`, `response(204).empty()`,
`response('5XX').text(body, { status: 503 })`), with `response.untyped(...)` and
`mock.untyped` as escape hatches.

**Why the opposite call from `openapi-react-query`.** There, every v1 requirement
replaced something the dependency did — key canonicalization, error typing,
middleware, tags — and its `queryFn` was internal, so none of it was overridable.
Here nothing needs replacing. What v1 adds — environment-neutral setup, the reset
convention, stateful fixtures, origin matching — sits *above* the handler factory
rather than inside it. Reimplementing its response-map inference (the
status → media-type → body walk, the no-content conversion, the object-union
smoosh, the wildcard table) would be a few hundred lines of type-level code to
arrive at the same types.

**Risk accepted.** It is a single-maintainer package released irregularly, which
its own README says plainly. The mitigation is that it is small, substantially
types-only, and reached through `createMockApi` rather than imported directly by
consumers — so replacing it with a fork or a hand-roll is a change inside this
package.

`createMockApi` is therefore a thin wrapper over `createOpenApiHttp`, and says so.
It earns its place by owning the origin-matching decision below, pinning one msw
peer range and one `openapi-msw` version for every consumer, keeping the name
alongside `createApiClient`/`createQueryApi`, and giving the package one import
surface to swap behind.

## Why `msw` is a peer dependency

The consumer owns the msw version, for a reason beyond convention: msw's
`mockServiceWorker.js` is generated by `msw init` from the installed library and
is version-checked at start. Two copies of msw in a tree also means two
interceptor registries, where handlers registered through one do not see requests
intercepted by the other.

The declared range is `^2.10.5` — `openapi-msw`'s own floor, and the msw 2.x line
throughout. There is no msw 1.x support and no plan for any.

## Handler path and origin matching

A handler path is `${base}${openApiPath}` with braces converted to msw's colon
form: `createMockApi({ baseUrl: '/api' })` plus `/things/{id}` matches
`/api/things/:id`. Trailing slashes on `baseUrl` are stripped, so `'/api/'` and
`'/api'` behave identically.

An **origin-relative** `baseUrl` is prefixed with msw's `*` wildcard by default,
which needs justifying because it is a departure from what msw does on its own:

- msw resolves a relative handler path against `document.baseURI` in the browser.
  Under `setupServer` there is no document, so it leaves the path relative — and
  every request URL in node is absolute, so a relative handler matches nothing.
  Handlers that work in the browser silently answer no requests in vitest.
- `*/api/things` matches on any origin, in both environments. That is what lets
  one handler array serve dev, vitest, and Playwright, which is the point of the
  environment-neutral setup below.

The trade-off is deliberate: a wildcard origin will also intercept a third-party
request that happens to share the path prefix. `origin: 'exact'` opts out and
keeps paths relative, at the cost of node tests needing an absolute `baseUrl` of
their own. An absolute `baseUrl` already pins the origin, so the setting does not
apply to one.

## Setup contract

`setupMocks(handlers, { onReset })` returns a plain description — the handler
array plus its state resets — and holds no msw setup object. That is what makes it
environment-neutral: the same value is handed to `setupMockWorker` in the browser
or `setupMockServer` under node.

The two environments are **separate entry points**, not a runtime branch:

- `@archon-research/http-client-msw/browser` imports `msw/browser`
- `@archon-research/http-client-msw/node` imports `msw/node`
- the root entry imports neither, so it resolves from either environment

A runtime `typeof window` check would put both imports in every bundle —
`msw/node`'s interceptors patch node's http modules, which has no business in an
app bundle, and the worker machinery has none in a test process.

### Reset

`reset()` on either entry runs the setup's `onReset` callbacks and then msw's own
`resetHandlers()`. One call, both kinds of leakage: state a handler *wrote* during
a test, and handlers a test *installed* through `server.use`. Handlers are
declared once with their resets, so a suite's `afterEach` is a single line and
cannot forget one of the two.

The reset callbacks are plain functions rather than objects with a `reset` method,
so anything can join the convention: `onReset: [rng.reset, store.reset, () => {
scenario = 'default'; }]`.

They run **in declaration order**, and that order is load-bearing whenever one
reset feeds another. A store whose seed function draws from a seeded rng must be
listed *after* the rng: reset the store first and it re-seeds from wherever the
sequence happens to be, so the fixtures change on every reset — which defeats the
determinism the rng exists for. Two specs in `src/setup.test.ts` pin both the
correct order and the drift, so the advice cannot quietly stop being true.

### Worker start

`start()` is idempotent — repeated and concurrent calls share one registration.
Registering the worker again mid-session resets its handler list, which would
silently drop runtime overrides a Playwright fixture had installed. An app entry,
a hot reload, and a test fixture may all reasonably call `start()`.

The memo is invalidated in the two cases where it would otherwise lie: a rejected
start, so a caller can retry after fixing whatever failed; and `stop()`, because a
memo pointing at a stopped worker resolves immediately and intercepts nothing —
the failure mode there is requests reaching the real network with no error at all.

The worker script URL is the app's **public base path**
(`import.meta.env.BASE_URL` under Vite) with the script filename appended, a
missing trailing slash inserted, and an empty base treated as `/` — not the API
base. A service worker's scope is limited to the directory it is served from, so a
subpath deployment must load the script from under that subpath.

Defaults differ per environment, in both cases away from msw's own:

- browser `onUnhandledRequest: 'bypass'`, `quiet: true`. An app in mock mode still
  loads its own documents, modules, images and fonts; warning on each buries the
  requests anyone is actually looking at.
- node `onUnhandledRequest: 'error'`. In a suite an unmocked request is a hole in
  the fixtures, and a warning that scrolls past is how a test ends up asserting
  against real network output.

## Stateful fixtures

Three small optional imports, no additional dependencies. Each exists because of a
specific way mocks fail:

- **`createMockStore(seedFn)`** — a POST that does not show up in the next GET
  makes any flow past the first screen untestable. Deliberately not a database:
  no queries, no indexes, no relations. A mock needing those is standing in for
  logic the real service owns, and the test belongs against the real service. The
  seed is a *function*, re-run on every reset, so a handler mutating an item in
  place cannot corrupt the next test's starting point — provided the function
  constructs its items rather than returning a shared array. Unknown ids return
  `undefined`/`false` for a handler to turn into its own 404; a duplicate insert
  throws, because that is a fixture bug rather than an API state.
- **`createSeededRng(seed)`** — `Math.random` in a mock makes a failing test
  unreproducible and a visual snapshot unstable. mulberry32: 32 bits of state and
  a handful of integer ops, cheap enough to call inside a handler. Statistical
  quality is irrelevant; reproducibility is the requirement.
- **`mockDelay(ms | { test, dev })`** — latency is what makes an app exercise
  pending, skeleton, and race states, and the same latency in a suite is dead
  time. A plain number applies in dev and is skipped under test; an object sets
  both. Zero resolves without a timer, so a suite's timing behaviour is unchanged.

## Deliberately out of v1

- **Handlers generated from the OpenAPI document.** A `.json` document could yield
  a default handler per operation from its schemas or `example` values. Skipped:
  the useful part of a mock is the state and the specific shapes a screen needs,
  and a generated body satisfying the schema is not that. The types already
  guarantee correctness; the fixtures supply meaning.
- **Runtime request-body validation.** `createQueryApi` validates *responses*
  against the document because a real server can lie. A handler's inputs are
  already typed at the boundary the mock controls, so the check would only catch
  an app sending something its own types forbid.
- **Named scenarios and a scenario switcher.** Toggling between mock states
  ("empty", "error", "slow") from a dev toolbar is real, but the shape it should
  take depends on the surface driving it. `server.use` and a store are enough
  until a consumer has one.
- **GraphQL and websocket typing.** `MockSetupHandler` accepts msw's
  `WebSocketHandler` so an untyped one can travel in the same array, but nothing
  derives ws or GraphQL handlers from a schema.
- **Per-test handler isolation.** msw's `boundary` API scopes handlers to an async
  context. The reset convention covers the sequential case; concurrent tests
  sharing one store would need it, and no consumer runs those yet.
- **Fault injection.** No chaos helper for random failures or dropped connections.
  A handler that returns an error status is one line, and a random one is a flaky
  test.
